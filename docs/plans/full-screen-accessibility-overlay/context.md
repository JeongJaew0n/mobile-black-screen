# context — full-screen-accessibility-overlay

## 사용자의 원 요청

> "아니 문제가 있잖아. 내가 원하는건 앱 위에서 screen off를 하면 해당 앱은 그대로 있고,
> 화면이 어두워 지는건데, 지금 여기서 만든앱은 여기 앱으로 이동해서 화면을 검게 만드는
> 방식이야. 이건 단단히 잘못됐어. 근본부터 다시 검토해."

## 왜 이걸 하게 됐는가 — 설계가 요구에서 벗어난 경위

이 작업은 **새 기능 추가가 아니라 잘못된 기본값을 바로잡는 일**이다.

작업 초기에 사용자는 두 해석 중 하나를 명시적으로 골랐다.

> "1. 다른 앱들이 계속 돌아가는 상태에서 화면만 덮기야."

그런데 완성된 앱의 기본값은 정반대였다. `BlackoutActivity` 로 **전환**해서 화면을 덮었고,
쓰던 앱은 뒤로 밀려났다.

### 어디서 어긋났는가

`TYPE_APPLICATION_OVERLAY` 가 상태바를 덮지 못한다는 사실을 실측으로 확인한 뒤,
**"오버레이는 상태바를 못 덮는다"를 모든 오버레이에 적용**해 버렸다. 여기서
"완전히 검게 하려면 Activity 로 전환하는 수밖에 없다"는 잘못된 전제가 생겼고,
그 전제 위에서 Blackout 이 기본값이 되었다.

접근성 서비스는 초기 분석에 등장하기는 했다. 다만 **"최상단 Activity 를 감지하는 수단"**
으로만 검토하고 "이 용도에 과하다"며 기각했다. **오버레이 레이어로서의 가능성은
검토조차 하지 않았다.**

`TYPE_ACCESSIBILITY_OVERLAY` 는 상태바·내비게이션 바·시스템 다이얼로그 위까지 덮는다.
이걸 진작 봤다면 하이브리드도, 잘못된 기본값도 없었다.

**남길 교훈: 제약을 말할 때는 어떤 창 종류에 대한 제약인지 반드시 붙일 것.**

## 결정된 방향

**접근성 오버레이로 화면 전체를 덮는 `FULL` 모드를 만들고 기본값으로 둔다.**
기존 두 모드는 남기되 역할을 재정의한다.

| 모드 | 쓰던 앱 | 상태바·내비바 | 권한 | 역할 |
|---|---|---|---|---|
| **FULL** | **유지** | **전부 덮음** | 접근성 | **기본. 원래 하려던 동작** |
| OVERLAY | 유지 | 남음 | 다른 앱 위에 표시 | 접근성을 주기 싫을 때 |
| BLACKOUT | 밀림 | 덮음 | 없음 | 권한을 하나도 주기 싫을 때 |

## 기각된 대안

- **`FLAG_LAYOUT_NO_LIMITS` 등 플래그 조합으로 일반 오버레이를 확장** — 기각.
  이미 실패가 실측으로 확인되었다. 창 프레임이 `[0,94][1080,2214]` 로 잘리고
  z-order 상으로도 시스템 바가 위다. 기하학·레이어 양쪽에서 막혀 있다.
- **Blackout 을 기본으로 유지하고 안내만 보강** — 기각. 사용자가 고른 요구 자체를
  충족하지 못한다.
- **접근성 서비스로 최상단 Activity 를 감지해 오버레이를 조정** — 불필요해졌다.
  애초에 Activity 전환을 안 하므로 감지할 이유가 없다.

## 제약 / 합의 사항

- **접근성 권한은 심리적 허들이 크다.** 개인용 사이드로딩이라 Play 정책 문제는 없지만,
  사용자가 설정에서 직접 켜야 한다. 그래서 FULL 이 기본값이되 권한이 없으면
  안내 카드를 띄우고 다른 모드로 쓸 수 있게 남겨 둔다.
- **앱을 재설치하면 접근성 서비스가 꺼진다.** Android 의 정상 동작이다.
- 이 서비스는 **화면 내용을 읽지 않는다**(`canRetrieveWindowContent=false`).
  접근성 서비스로 등록하는 유일한 이유는 `TYPE_ACCESSIBILITY_OVERLAY` 자격이다.
