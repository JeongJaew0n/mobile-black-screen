# context — media-volume-control

> **이 문서는 사후에 고쳐 쓰지 않는다.** 작성 시점(2026-09-21)의 판단 기록이다.
> **조사·설계 단계. 구현 전.**

## 원 요청

> "혹시 블루투스 외의 소리 차단 기능도 넣을 수 있어?
> 음... 미디어 소리만 차단하면돼.
> '검은화면 켰을 때 미디어 소리를 0으로 줄임' 기능과
> '검은화면 일 때 미디어 소리 일시 음소거' 기능을 넣자.
> 소리 0은 진짜 0으로 만들어서 다시 화면켜도 그대로 0이고,
> 음소거는 차폐때만 음소거 됐다가 풀면 원래대로 되돌아오는 기능이야."

처음 "블루투스 외의 소리" 라고 했다가 곧 **"미디어 소리만"** 으로 좁혔다. 이 문서는 좁힌 쪽을
따른다 — 알림·통화·알람 소리는 건드리지 않는다.

## 두 기능은 무엇이 다른가

같은 "소리를 끈다" 지만 **되돌아오는가**가 다르다.

| | 차폐 시작 | 차폐 해제 후 |
|---|---|---|
| **볼륨 0** | 미디어 볼륨을 실제로 0 으로 내린다 | **0 그대로.** 사용자가 직접 올려야 한다 |
| **일시 음소거** | 음소거한다 | **원래 볼륨으로 돌아온다** |

전자는 "잘 때 소리 나면 안 되니 아예 꺼 둔다", 후자는 "차폐 중에만 조용히" 다. 둘은 배타적이라
설정에서 **셋 중 하나(끔 / 일시 음소거 / 볼륨 0)** 로 고르게 하는 것이 맞다. 스위치 두 개로
두면 둘 다 켰을 때 무엇이 이기는지 사용자가 알 수 없다.

## 이 앱의 다른 기능과 정면으로 충돌한다 — 그래도 넣는 이유

**재생 바(`docs/plans/media-playback-bar/`)의 존재 이유가 "유튜브 소리를 들으면서 화면만 끄기"** 다.
FULL 모드가 아래 앱을 멈추지 않는다는 성질에서 나온 가장 실용적인 부수 효과였다.
소리를 끄는 기능은 그 용도를 정확히 무효로 만든다.

그럼에도 넣는 이유는 **두 용도가 서로 다른 때에 쓰이기 때문**이다. 음악을 들으며 화면을 끄는
때가 있고, 알림 소리 없이 조용히 두고 싶은 때가 있다. 한쪽을 위해 다른 쪽을 포기할 일이 아니다.

그래서 **기본값은 반드시 "끔"** 이다. 이 앱의 기본은 "아무것도 하지 않는 완전한 검정" 이고,
소리를 건드리는 것은 사용자가 명시적으로 켜야 하는 동작이다.

## 갇힘 문제와 닮았지만 훨씬 덜 위험하다

지문 해제에서 겪은 것과 같은 모양의 위험이 있다 — **앱이 복원에 실패하면 사용자가 원치 않는
상태에 갇힌다.** 차폐를 푸는 경로가 여럿이고(제스처·지문·시스템이 창을 걷어감·서비스 종료·
강제 종료), 그중 하나라도 복원을 놓치면 음소거가 남는다.

다만 결정적 차이가 있다. **볼륨은 사용자가 물리 키로 언제든 되돌릴 수 있다.**
차폐에 갇히면 화면을 되찾을 방법이 없었지만, 음소거가 남으면 볼륨 키를 누르면 끝이다.
그래서 지문 때처럼 겹겹의 안전망을 쌓을 필요는 없고, **복원 지점을 빠짐없이 거는 것**으로 충분하다.

## 조사 결과 — 무엇이 되고 무엇이 불확실한가

### 확실한 것

- **미디어 볼륨은 `AudioManager.STREAM_MUSIC`** 이다. 알림·통화·알람과 분리된 스트림이라
  "미디어만" 이라는 요구를 그대로 만족한다.
- **볼륨 조작에 새 권한이 필요 없다.** `ACCESS_NOTIFICATION_POLICY`(방해 금지 권한)는
  벨소리·알림 스트림을 무음으로 만들 때 요구되는 것이고, `STREAM_MUSIC` 은 대상이 아니다.
  이 앱은 이미 특수 권한을 셋(접근성·다른 앱 위에 표시·알림 접근) 받고 있어 **넷째를 더하지
  않는 것이 중요하다.**
- **볼륨 UI 팝업은 `flags = 0` 으로 끌 수 있다.** `FLAG_SHOW_UI` 를 주지 않으면 시스템
  볼륨 슬라이더가 뜨지 않는다. 차폐 위에 팝업이 뜨면 "완전한 검정" 이 깨지므로 반드시 0 이어야 한다.

### 실측으로 확인해야 하는 것

> 아래는 **추정이며 코드로 확정하지 않았다.** 구현 첫 단계에서 실기기로 확인하고 이 문서를
> 실측값으로 고친다. 지금까지 이 저장소에서 틀린 것은 대부분 "문서를 안 보고 일반화한 것"
> 이었다(`overlay-window-cannot-cover-status-bar.md`).

1. **`adjustStreamVolume(STREAM_MUSIC, ADJUST_MUTE, 0)` 이 권한 없이 동작하는가.**
   시스템이 이전 볼륨을 기억했다가 `ADJUST_UNMUTE` 로 되돌려 주므로, 우리가 값을 저장·복원하는
   것보다 안전하다. 다만 이 API 는 버전·제조사별 동작 차이가 알려져 있다.
2. **시스템 음소거가 우리 프로세스 수명과 무관한가.** 무관하다면 앱이 강제 종료돼도 음소거가
   남는다 — 그 경우 `ADJUST_MUTE` 대신 **직접 볼륨을 저장하고 0 으로 내리는 방식**이 낫다.
   어느 쪽이든 복원 실패 시 볼륨 키로 회복 가능하지만, 덜 놀라는 쪽을 골라야 한다.
3. **블루투스·이어폰이 연결돼 있을 때 어느 볼륨이 바뀌는가.** Android 는 출력 장치별로 미디어
   볼륨을 따로 기억하고, 블루투스는 기기가 절대 볼륨을 관장하는 경우가 있다.
   사용자가 처음에 "블루투스 외의 소리" 라고 말한 것이 이 지점과 관련 있을 수 있다 —
   **블루투스 스피커로 듣는 중에 차폐를 켜면 그 소리까지 꺼지는 것이 의도인지** 확인이 필요하다.
4. **차폐 중 사용자가 볼륨 키를 누르면 어떻게 되는가.** 볼륨이 올라간다. 그것을 되돌리려
   감시하면 볼륨 키가 무력화되어 사용자가 소리를 되찾을 수 없다 — **감시하지 않는다**는 것이
   현재 판단이지만, 그러면 "일시 음소거" 가 사용자 조작 한 번에 풀린다는 뜻이기도 하다.

## 기각한 대안

| 대안 | 기각 이유 |
|---|---|
| 모든 스트림 음소거 | 알람·전화를 놓친다. 사용자가 "미디어만" 으로 좁혔다 |
| `AudioManager.requestAudioFocus` 로 다른 앱 재생을 멈춤 | 소리를 줄이는 게 아니라 **재생 자체를 멈춘다.** 재생 바가 보여 줄 것이 없어지고, 앱에 따라 포커스를 돌려줘도 재생이 안 돌아온다 |
| 스위치 두 개(0으로 / 음소거) | 둘 다 켜면 무엇이 이기는지 알 수 없다. 라디오 3택이 맞다 |
| 차폐 중 볼륨 키 감시해 계속 0 유지 | 사용자가 소리를 되찾을 수단을 뺏는다. 갇힘의 작은 판본이다 |
